# AI Tool Rules - Forensic Council

These rules protect the stable app baseline and apply to every AI coding tool,
local assistant, remote assistant, script generator, and human applying generated
changes.

Stable rollback point:

- Tag: `stable-2026-05-17`
- Commit: `8909d3a3b248e3ef036cc50747dd8b51ef4282c1`
- Remote: `origin/main`

If a change breaks the app, revert to the stable tag instead of improvising:

```bash
git switch main
git reset --hard stable-2026-05-17
```

Only run the reset command after the maintainer explicitly approves losing local
changes.

---

## Required Reading Before Any Edit

Read these in order before changing files:

1. `AGENTS.md`
2. `PROJECT_HANDOFF.md`
3. `FULL_APP_AUDIT.md` if present locally
4. The exact files you intend to edit

Do not rely on guesses from memory. The current code is the source of truth.

---

## Non-Negotiable Product Invariants

Never remove, bypass, fake, or weaken:

- authentication and authorization
- MIME and extension validation
- file size validation
- evidence hashing
- chain-of-custody logging
- report signing
- quota checks
- rate limiting
- HITL checkpoint logic
- WebSocket/SSE progress logic
- Arbiter finalization
- backend-generated forensic reports
- production secret validation
- same-origin Docker/Caddy proxy behavior

The frontend must not hardcode forensic verdicts, fabricate reports, or display
fake analysis as if it came from the backend.

---

## Scope Discipline

Before editing, write down the narrow goal in the handoff or commit notes.

Allowed:

- small, targeted fixes
- docs that match actual code
- tests covering the changed behavior
- local refactors only when they reduce real duplication or match an existing pattern

Stop and make a sub-plan before editing if a change:

- touches more than 5 files
- changes more than roughly 200 lines
- crosses frontend/backend/infrastructure boundaries
- changes auth, custody, signing, quota, rate limiting, HITL, upload flow, or report flow
- alters Docker networking, production env validation, or migrations

Do not mix unrelated fixes in one commit.

## Frontend Flow Must Remain Intact

Preserve this path:

```text
/ -> upload modal -> pendingFileStore -> /evidence -> useInvestigation
-> POST /api/v1/investigate -> WebSocket updates -> HITL if needed
-> deep analysis/resume -> /result/{sessionId}
```

Do not move pending file state into persistent storage. Do not bypass
`startInvestigation`, `connectWebSocket`, or result fetching.

---

## Backend Flow Must Remain Intact

Preserve this path:

```text
POST /api/v1/investigate -> validate evidence -> hash evidence
-> create session -> launch/queue pipeline -> run agents -> HITL pause/resume
-> Arbiter finalization -> signed report persistence -> report fetch
```

Do not skip session persistence, custody entries, report signing, or centralized
finalization.

---

## Environment And Dependency Rules

- Do not add paid-provider defaults.
- Do not leak API keys or secrets to frontend code, logs, docs, screenshots, or tests.
- Do not change Python, Node, Debian, CUDA, or base image versions without a separate
  dependency phase and verification.
- Do not remove strict Docker Compose required-env syntax (`${VAR:?message}`).
- Do not loosen production readiness checks.
- Do not change lockfiles unless the package manifest changed or the maintainer asked.
- Do not introduce new runtime dependencies when the standard library or existing
  project dependency is enough.

## Verification Required Before Handoff

Always run:

```bash
git diff --check
python scripts/check_docs.py
```

If `python scripts/check_docs.py` runs on Windows and fails only because WSL's
`bash.exe` exists but has no installed Linux distribution, rerun it with a
Windows-safe PATH that excludes `C:\WINDOWS\system32\bash.exe`, then record that
in `PROJECT_HANDOFF.md`.

For frontend changes, run from `apps/web`:

```bash
cmd /c npm run type-check
cmd /c npm run lint
cmd /c npm test
```

For backend Python changes, run from `apps/api` when dependencies are available:

```bash
uv run ruff check .
uv run pytest
```

If dependencies are unavailable, at minimum run targeted syntax checks:

```bash
python -m py_compile <changed-python-files>
```

For Docker or infra changes, run the relevant compose config or project verifier
documented in `PROJECT_HANDOFF.md`.

Never claim a check passed unless it actually completed with exit code 0.

---

## Handoff Rule

After every meaningful local change, update `PROJECT_HANDOFF.md` with:

- what changed
- files touched
- tests or checks run
- commands that failed
- known risks
- next action

If the work is committed and pushed, record the commit SHA and tag if one was
created.

---

## Commit And Push Rules

- Use one commit per coherent change.
- Keep commit messages product-focused.
- Do not rewrite public history or force-push without explicit maintainer approval.
- Create a stable tag after a known-good release checkpoint.
- Push tags with the commit when the maintainer asks for a rollback point.

Recommended stable tag format:

```bash
git tag -a stable-YYYY-MM-DD -m "stable: short checkpoint description"
git push origin main stable-YYYY-MM-DD
```

---

## Quality Bar

Prefer boring, readable, well-tested fixes over clever rewrites.

When uncertain, inspect the code, narrow the scope, and preserve the existing
architecture. The app is a forensic evidence system, so correctness, traceability,
and rollback safety matter more than speed.
